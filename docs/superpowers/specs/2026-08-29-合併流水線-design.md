# 合併流水線設計 — 新負血劍譜5 併入 無法無天

日期：2026-08-29
狀態：待使用者核可
參與決策：使用者逐段核可（§1、§2 已核可；§3 修正為固定檔名後核可；§4 核可）

## 1. 目標

以 `古龍921_無法無天.aoe2scenario` 為基底，把 `古龍921_新負血劍譜5.aoe2scenario`
的遊玩內容（由使用者圈選）合併進來，並套用原「劍譜5 施工計畫」的全部工項
（攻擊力修復、雙0血、caption 血條、436→2353 等），產出單一合併版成品。

硬性要求：
- **異動紀錄**：每個變更步驟都留痕，包含但不限於觸發變動（物件增刪、文字、數值都算）。
- **單一入口寫檔**：全專案只有 `build.py` 會寫劇情檔，從 origin/ 乾淨基底重跑一次即可從零重建成品。
- **測試指引**：每次建置自動生成一份給使用者的實機測試指引，說明本輪改了什麼、進遊戲驗什麼、怎麼判讀。

## 2. 已確認的決策

| 決策 | 結論 |
|---|---|
| 合併範圍怎麼定 | **先盤點再圈選**：先產差異盤點報告，使用者逐組圈選，圈選結果寫入 `merge_spec.yaml` 成為合併規格 |
| 與劍譜5 施工計畫的關係 | **全部改對準合併版**：唯一產品是合併版，不再單獨修劍譜5 |
| 異動紀錄形式 | **雙軌**：機器可比對的 TSV ＋ 人讀的 md 摘要 |
| 中間產物 | **單腳本＋`--until`**：平常一次寫到底只出最終檔；要驗某步用 `--until` 出中間檔。中間檔與成品不進 git，只有 log 進 git |
| log 版本管理 | **固定檔名，不留時間戳副本**：每次建置覆寫同一組檔，歷史由 git 承擔，一輪建置一個 commit |
| 合併機制 | **方案 C 混合**：依賴度乾淨的觸發組用自動搬運器，跟基底糾纏的組逐一手寫補丁 |

介面約定：
- steps 都是純函式：`apply(scenario, spec) -> list[Change]`，自己不讀寫檔案。
- `Change` 是統一的異動資料結構（step、kind、target、field、old、new、reason、測試提示），
  log 與測試指引都從它生成——step 不可能「改了但沒記錄」。
- `build.py` 用法：
  - `python build.py` — 從 origin 跑到底，寫 `out/古龍921_合併.aoe2scenario`
  - `--until s30` — 只跑到 s30，出中間檔供實機驗證
  - `--deploy` — 順手複製產出檔到遊戲劇情資料夾
    `C:/Users/Ricky/Games/Age of Empires 2 DE/76561198023399153/resources/_common/scenario/`
- 寫檔前設定 `trigger_manager.legacy_execution_order = True`（鐵律）。
- 絕不從 DE 編輯器存檔（鐵律，編輯器會正規化刻意寫入的溢位值）。

## 5. 流水線階段（已核可）

| 階段 | 做什麼 | 規格出處 |
|---|---|---|
| （建置外）盤點 | 產差異盤點報告 → 使用者圈選 → 寫進 merge_spec.yaml | §7 |
| s10 自動搬運 | 圈選為「自動」的劍譜5 觸發組＋所屬物件搬進無法無天；重映射觸發索引引用（Activate/Deactivate Trigger 的 trigger_id）與物件 ref | 方案 C |
| s20* 手寫補丁 | 糾纏組逐一接線，一組一支腳本，接線決策寫在腳本 docstring | 方案 C |
| s30 攻擊力修復 | 對合併後全檔跑還原公式 V=(高16位)×256＋(低16位)，class=0 | 遷移記錄 §3.3e |
| s40 雙0血 | 先對合併版重跑建築血量盤點（三種目標模式都解析）找出對應 ref，再灌雙0血 | 遷移記錄 §5.7 |
| s50 血條 | caption 血條 ×2，每目標 100 階梯，格式 `名稱 [####______] 40%`（半形 %） | 遷移記錄 §5.7a |
| s60 雜項 | 436→2353 這類替換；合併版要先重查 436 是否仍存在 | 遷移記錄 待辦節 |
| s90 終檢 | 不變量稽核（見 §8），任一失敗 build 中止、不出檔 | audit.py 改裝 |

順序理由：**先合併再修復** —— 搬入的劍譜5 觸發同樣帶著轉檔損壞，
s30 放在合併後可一次修兩邊，不必各修一遍。

依賴注意：s50 的血條刻度需要實機讀「s40 雙0血套用後的起始當前血量」，
所以 s50 的階梯門檻值放在 merge_spec 的參數區，先用估值建置 → 使用者實測回報 → 改參數重建。

## 6. 異動紀錄與測試指引（已核可，含固定檔名修正）

`logs/` 下固定檔名，每次建置覆寫，git 承擔歷史，一輪建置一個 commit：

**① 機器檔 `NN_步驟名.tsv`** — 逐筆 old→new：

```
step	kind	target	field	old	new	reason
s10	trigger_add	T5599「幫眾」	—	—	(來自劍譜5 T4102)	merge_spec: 幫眾系統
s10	remap	T5599 效果3	trigger_id	4103	5600	搬運自動重映射
s30	effect	T210 效果0	quantity	16646156	+65036(class0)	§3.3e 還原公式
s40	unit	ref31245 聚魂塔	hp	—	雙0血	§5.7
```

**② 人讀檔 `NN_步驟名.md`** — 每步：改了什麼、為什麼（引規格出處）、影響範圍、風險備註。

**③ 測試指引 `logs/測試指引.md`** — 整輪彙總，按「進一次遊戲能驗完」的順序組織：

```
### 驗 s40 雙0血
改變：亡魂之堡、聚魂塔等 N 目標改為雙0血
怎麼測：進遊戲後派兵攻擊亡魂之堡
預期：血量實際下降（不再彈回滿血）
異常判讀：血量凍在最大值＝夾血未解除，回報「s40 失敗＋截圖」
```

生成機制：每個 step 自帶測試模板（宣告「我改了 X，驗法是 Y」），
build 時代入實際 Change 清單的對象名與數字自動生成；
改動為零的步驟自動標「本輪無異動，免測」。

## 7. 盤點報告方法（已核可）

一次性唯讀分析，產 `reports/盤點報告.md`，四步：

1. **觸發配對**：先名稱精確配對；配不上的（41 vs 317）按內容指紋
   （條件/效果類型序列＋參數雜湊）做相似度配對，把改名觸發對上。
   剩下真正單邊獨有的才是搬運候選。
2. **分群成系統**：用啟動關係圖（Activate/Deactivate 邊）把觸發連成群，
   輔以名稱前綴。每群是一個圈選單位。
3. **每群評依賴度**：群內引用的物件是否都在 10,249 個兩版相同物件內？
   啟動邊有沒有跨進基底觸發？→ 標 `自動搬運` / `需手寫補丁` / `建議不搬`。
4. **同名不同內容清單**：兩版都有但參數不同的觸發（敵人強度改版這類），
   預設以無法無天為準；差異大的列給使用者過目，防「以為一樣其實被改掉」。

報告格式：開頭一張總表供直接圈選；每群一節（名稱、一句話功能摘要、
觸發/物件數、依賴度標記、建議）；物件差異按區域＋所屬觸發群歸類附在各群下；
無觸發引用的孤兒物件（裝飾物）單獨一節。

## 8. s90 終檢不變量

- 攻擊力效果無殘留壞編碼（|值|≥65536 且非刻意寫法者 = 0）
- 所有 Activate/Deactivate Trigger 的 trigger_id 落在有效範圍
- 所有效果的 selected_object_ids 指向存在的物件 ref
- `legacy_execution_order = True` 已設
- 觸發總數、效果總數與各 step 宣告的增量對帳相符
- 雙0血目標清單與 s40 實際寫入清單一致

任一失敗：build 非零退出、不寫 out/、log 記失敗原因。

## 9. 測試策略

- 每輪建置後使用者照 `logs/測試指引.md` 實機驗（單人→劇情，鐵律）。
- 合併初期用 `--until s10` 先驗「搬運後基底功能未壞」（抽測無法無天原有主線），
  再逐步放行後續階段。
- 引擎級結論（負進貢、-1 哨兵、Object Visible 語意等）沿用劍譜5 驗證成果，
  不重測；檔案級事實（ref 編號、436 存在性、起始血量）一律在合併版上重查。
