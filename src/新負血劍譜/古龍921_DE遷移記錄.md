## 第一部分：引擎欄位事實

### 1.1／1.2／1.2b 血量雙欄位、參數型別、int16 回繞

→ **通用指南 §2.1~§2.3**。

### 1.2c `改變目標生命值` 是**相加（ADD）**，不是設定（等級 A — 實測確認 2026-08-28）

⚠️ **這推翻了本規則書早期版本所有以「設定」為前提的血量推論。**

`ZZ_test01b_負血重測` 三種 operation 並排實測結果：

| lane | operation | 存活 | 血量 | 結論 |
|---|---|---|---|---|
| L1 | **-1**（本體 790 個效果全用此值） | 存活 | 45 | **與 ADD 相同** |
| L2 | 1 = SET | **死亡** | — | 真的設成回繞負值 → DE 殺死單位 |
| L3 | 2 = ADD | 存活 | 45 | 校準基準 |

→ **`operation = -1` 在 DE 等同 ADD。**
→ 若真的用 SET 把最大血量設成回繞負值，**DE 會殺死單位**（證實 `UGC` 的 "will die because of an overflow"）。

**AoC 同樣是 ADD**，由 `NAKUZ` 自身文本反證（等級 A）：

1. **Q68 第三步 `參數：A - 32767` 標註「還原」**——只有相加才能還原：
   先加 `32767 - A`、再加 `A - 32767`，正好抵銷回原值。若是設定，設成負數不可能叫還原。
2. **Q61 的名稱就是證明**：`參數：65536 - 單位上限值` 相加後 =
   `A + (65536 - A) = 65536`，int16 回繞 = **0** → 這正是「**雙0血**」(HP 0/0)。

→ **AoC 與 DE 語意一致，本體 790 個效果沒有語意落差。** ✅

**第三個佐證**：把測試檔在 DE 編輯器裡開啟再存檔後，原本 `operation = -1` 的效果
被寫回成 **`operation = 2`**。DE 編輯器主動把 -1 正規化成 ADD。

推論（等級 B）：若日後用 DE 編輯器開啟本體戰役並存檔，那 790 個 `-1` 會全部變成 `2`。
語意相同所以行為不變，但**檔案內容會被改寫**，做位元組比對時要留意。

### 1.2d 正確的計算方式（等級 A — `ZZ_test01c` 實測確認 2026-08-28）

每個 `改變目標生命值` 是「**累加**後 mod 65536」，最終最大血量為：

```
最大血量 = 單位基礎血量 + int16( Σ 所有已執行效果的參數 )
```

**且：最大血量 ≤ 0 時單位死亡。界線精確落在 0。**

`ZZ_test01c` 實測（Man-at-Arms 基礎血量 45，operation 全為 -1）：

| lane | 累加 | 預期血量 | 實測 |
|---|---|---|---|
| C1 | −44 | 1 | **存活，顯示 1** ✅ |
| C2 | −45 | 0 | **死亡** ← 0 血即致命 |
| C3 | −46 | −1 | **死亡** |
| C4 | −250 | −205 | **死亡** |
| C5 | +12038, +53518 | 65 | **存活，顯示 65** ✅ |
| C6 | +11468, +53818（回繞得 −250） | −205 | **死亡** |
| C7 | 對照組 | 45 | **存活，顯示 45** ✅ |

推論：
- **C4 與 C6 結果相同** → 回繞產生的負值與直接給的負值行為一致，無隱藏差異 ✅
- **C5 = 65 精確驗證算式**：`12038 + 53518 = 65556`，`65556 mod 65536 = 20`，`45 + 20 = 65`
  （測試文件原本誤寫「預期 62」，是把本體 `名` 的 −3 誤算進這條 lane，實測值才是對的）

### 1.2e `馬血` 的真正用途是**血量正規化**（等級 A — `ZZ_test01d` 實測，六隻全中）

用真實單位型別與真實數值實測，**預測值與實測值六個全部吻合，六隻全部存活**：

| 單位 | 基礎血量 | 淨增量 | 預測 | 實測 |
|---|---|---|---|---|
| Elite Mameluke | 80 | +17 | 97 | **97** ✅ |
| Henry V | 240 | −144 | 96 | **96** ✅ |
| Scythian Scout | 90 | +10 | 100 | **100** ✅ |
| Sir John Fastolf | 200 | −105 | 95 | **95** ✅ |
| Alexander Nevski | 230 | −134 | 96 | **96** ✅ |
| Tamerlane | 350 | −250 | 100 | **100** ✅ |

**最終血量全部落在 95～100。**

→ **`馬血` 不是「負血」技巧，而是血量正規化。** 作者把六隻基礎血量差異極大（80～350）
　 的英雄坐騎，全部校正到約 100。每隻參數不同正是因為各自需要的差值不同：

```
所需增量 = 目標血量 − 該單位基礎血量
負增量以 mod 65536 回繞表達（因為此效果只能相加）
```

→ **本體設計在 DE 完全按原意運作，這 6 個效果不需要任何修改。** ✅
→ 「負血」一詞指的是**中間狀態**（累計值 int16 為負），而非最終血量。

### 1.2f 「爆血」系統 —— `馬血` 正規化的真正理由（等級 A，來源：作者自述 + 觸發器內容）

作者在劇情說明／提示裡明確描述這套機制，並自稱是編輯器技巧：

> 「回血術, **爆血術**, 增加攻擊新增, (回血術與爆血術息息相關)」
> 「主要以回血數量速度, 攻擊力, **生命爆血秘訣**」
> 「**馬騎箭俠買神兵直接啟動6秒一次扣血**」
> 「箭客(暗殺者,武器駱駝)！免神兵倒每6秒扣血4000」
> 「重要解任務之運用 **(否則自取滅亡)** … **當你了解爆血技巧你已經擁有修改或者製作劇情的一些技巧了**」

實際觸發器：

| 觸發器 | 週期 | 效果 | 目標 |
|---|---|---|---|
| `[4678] 失血` | 6 秒 | `Damage Object` **+800000** | P1~P6 在區域 (0,0)-(113,12) 的單位；訊息「周賓魂使用了 化功大法 −HP800000」 |
| `[4729] 1失血` | **1 秒** | `Damage Object` **+6000** ×2 | 玩家角色 ref 0 **與其坐騎** ref 26109 |
| `[4730]~[4733]` | 1 秒 | +5400 ~ +6000 | 其餘職業的角色與坐騎 |

**啟用 `1失血` 的是 `[4709] 刀3`** —— 同一個觸發器同時給 **+21000 攻擊力**。

→ **設計意圖**：買神兵 = 攻擊力大幅提升 + 每秒扣 6000 血，靠回血術續命。這就是「爆血」。

→ **`馬血` 正規化的理由**：那六隻是六個職業的坐騎形態（刀馬俠…箭馬俠），
　 基礎血量 80~350 差了四倍多，但 `失血` 的扣血速率是統一的 5400~6000/秒。
　 **若不正規化，六個職業的續戰能力會因坐騎基礎血量不同而失衡。**
　 校正到同一基準（~100）是遊戲平衡需求。

→ 「負血」（`65536 - A` 穿越負值區回繞）是**唯一能用「只會相加」的效果達成「設定絕對值」的手段**。

### 1.2g ⚠️ 攻擊力損壞的實際後果（升級為最高優先）

1. 給 +21000 攻擊力 —— **DE 已切壞成 +8**（見 3.2 / 3.5）

### 2.1 負血（等級 A — 本戰役核心機制，戰役名稱由來）

```
改變目標生命值 ｜ 參數：65536 - A        →  最大血量 = -A
```

### 2.6 英雄式自動回血 — 浮點 ULP 技巧（本戰役**未使用**）

記錄於此僅供參考。全檔 5232 觸發器掃描 2^24~2^30 錨點，**零命中**。

完整結構（`NAKUZ` Q65 + 使用者提供的展開版）：
```
摧毀目標 ｜ 參數：-2^n + A      ← 把當前血量推到 2^n 這個精度台階
摧毀目標 ｜ 參數：-k            ← 重複 m 次，每次回 k 血
摧毀目標 ｜ 參數：+2^n - A      ← 減回來
```
簡化版把前兩個效果合併：`-2^n - k + A`

| 基礎值 | 2^n | 回血粒度 | n 值必須是 |
|---|---|---|---|
| 2^24 | 16777216 | 1 HP | 1 的倍數 |
| 2^25 | 33554432 | 2 HP | 2 的倍數 |
| 2^26 | 67108864 | 4 HP | 4 的倍數 |
| 2^27 | 134217728 | 8 HP | 8 的倍數 |
| 2^28 | 268435456 | 16 HP | 16 的倍數 |
| 2^29 | 536870912 | 32 HP | 32 的倍數 |
| 2^30 | 1073741824 | 64 HP | 64 的倍數 |

規則：
- 每個 `-k` **必須是獨立效果**。合併成 `-5` 只會做一次浮點加法，被 ULP 吃掉
- 「系統永遠由最上讀到最下」，故 `-2^n+A` 只能與**緊接的第一個** `-k` 合併
- 同一單位上若用多種基礎值，**只有基礎值最大的生效**
- 沒有比 2^30 更大的基礎值：2^31 超出 `摧毀目標` 的 int32 參數範圍
- 此法與僧侶治療不相容（`NAKUZ`）

### 2.8c 🔑 「不用負號」的溢位寫法 —— 這解釋了 `修1` 的 bug

> FAQ **Invincible Units Without Minus Sign**（70 血冠軍步兵）：
> ```
> Effect1: Change object HP 65466      (65536 − 70)
> Effect2: Damage object 4294967226    (4294967296 − 70)
> Effect3: Change object HP 70
> Effect4: Damage object 70
> ```

**AoC 編輯器無法輸入負號**（FAQ 另有一節專講：只能從訊息框或觸發器名稱複製貼上），
所以社群的標準變通寫法是：

```
想要 -N（最大血量，int16 欄位）  ->  填 65536 − N
想要 -N（當前血量，int32 欄位）  ->  填 4294967296 − N
```

**這正是本規則書 §1.2 那些 `65536 − A` 寫法的來源**，
也是為什麼 `operation` 必須是 ADD 才有意義（§1.2c）。

**關鍵限制：`4294967296 − N` 只在 N ≤ 2147483648 時有效。**
超過就會落回正數區間，公式**靜默失效**。

本體有兩個實例，一成一敗：

| 位置 | 作者填入（推算） | DE 讀到 | 結果 |
|---|---|---|---|
| `[4951] 馬` eff[24] | `4294967296 − 1,100,000,000 = 3,194,967,296` | **−1,100,000,000** | ✅ 成功（在範圍內） |
| `[5230] 修1` eff[19] | 想要 **−3,000,000,000** → 填 `1,294,967,296` | **+1,294,967,296** | ❌ **公式失效**，變成正傷害 |

→ **作者公式套對了，是目標值超出 int32 下限（−2147483648）導致的。**
→ **AoC 也是同樣的 int32 欄位 → 原作者 bug，不是 DE 迴歸。**

### 3.2 `改變目標攻擊力` — 被重新切分（等級 A）

DE trigger 格式 2.5 把攻擊力存成單一打包整數（來源 `PARSER`）：

```
DE trigger 2.4:  quantity = class × 256   + amount     （amount ≤ 255）
DE trigger 2.5:  quantity = class × 65536 + amount     （本檔案適用）
```

轉檔器把每個 AoC 值當成 2.4 格式的打包值重新切分再以 2.5 格式寫回：

```
DE_raw = (AoC >> 8) × 65536 + (AoC & 255)                    （AoC ≥ 0）
DE_raw = -( ((-AoC) >> 8) × 65536 + ((-AoC) & 255) )         （AoC < 0）
```

**問題**：原作者的值全是單純攻擊力數值，不是打包值。任何 |值| ≥ 256 的都被切壞。

### 3.3 攻擊力還原公式

→ **通用指南 §3.1**（`class×256 → class×65536` 完整公式與成對驗證法）。

### 3.3c ✅ 攻擊力：以實際傷害量測的定論（等級 A — `ZZ_test02d` 2026-08-28）

**UI 數字不可信**：同一個效果（class=0, amount=100），
`ZZ_test02b` 的提示框顯示「近戰 −94」、`ZZ_test02c` 的面板顯示「6+100」。
兩個 UI 互相矛盾，故改用**實際戰鬥傷害**當唯一判準
（靶最大血量 2045、已凍結不反擊、攻擊者原地防守、約 7 下）。

| lane | 編碼 | 剩餘血量 | 造成傷害 | 推得攻擊力 |
|---|---|---|---|---|
| E1 基準 | 未加成 | 2003 | 42 | **6** |
| **E2** | **class=0, amount=100** | **1303** | **742** | **106** ✅ |
| **E3** | class=4, amount=100 | **1303** | **742** | **106** ✅ 與 class 0 相同 |
| **E4** | **class=78, amount=32** | **2003** | **42** | **6** 🔴 **完全無加成** |
| E5 | class=4, amount=30000 | 靶死亡 | — | 極高 ✅ |
| E6 | class=0, amount=30000 | 靶死亡 | — | 極高 ✅ |

**結論：**

1. **`class=0, amount=N` 就是「攻擊力 +N」。** E2 與 E3 傷害完全相同。
   → 提示框的 `−94` 是**顯示假象**，不是實際攻擊力。

   UGC 指南的「quantity 上限 255」與實測不符。

```
V = (DE現值 >> 16) × 256 + (DE現值 & 0xFFFF)      ← 還原 AoC 原值
改寫成 change_object_attack(armour_attack_class=0, armour_attack_quantity=V, operation=ADD)

驗算 `火砲2`：`5111840` → `78 × 256 + 32 = 20000` → `class=0, amount=20000` ✅

→ 這是本次遷移**最嚴重**的單一迴歸，且與攻擊力修復無關（即使攻擊力仍壞，50 下也拆了）。
→ 原設計意圖確認：**最大血量刻意壓到 300、當前血量灌到 600 萬**，
　 正是 `毀僧聖僧`（`155,204,672 / 70`）那套手法用在建築物上。

算出 `39 × 256 + 16 = 10000`。量級完全吻合（差 3 點來自其他效果），
**證實 3.3e 的還原公式正確。** ✅

## 第五部分之六：`亡魂之堡` 最終定案（2026-08-28）

### 5.6 為何雙0血是唯一狀態（等級 A）

三個已實測的硬限制串起來，答案就唯一了：

| # | 事實 | 出處 |
|---|---|---|
| 1 | 最大血量以 **int16** 寫回，上限 32767 | 1.2、3.1 |
| 2 | **建築物**的當前血量會被**夾到最大血量** | 1.2k、1.2m（本體 `6000300/300` → DE `300/300`） |
| 3 | **只有 max = 0 時夾限不生效**，可持有 600 萬當前血量 | 1.2n / `01n`（N1、N3 挨打 30 秒存活；N2 只做第一步即死亡） |

由此可推導出兩個常見替代想法為何一定失敗：

- **「最大血量設成 100，每 N 傷害掉 1 格，用原生血條當進度條」**
  → 設定正的最大血量的那一瞬間，當前血量被夾成 100，**600 萬血池當場消失**。
    這正是 1.2m 那個 `6000300 → 300` 迴歸本身。
  → 且 100 血對上每下 3 萬傷害是一擊斃命，觸發器**來不及在同一 tick 補血**
    （`Heal Object` 每秒才評估一次，傷害是即時結算）。

- **「拉滿裝甲讓每下只造成最小傷害 1」**（AoE2 傷害下限恆為 1）
  → 技術上可行，但**神兵與木棍殺得一樣快**，攻擊力成長完全失效。
    本戰役的核心進程就是買神兵變強，此方案摧毀遊戲設計。**已否決。**

**結論：要同時保留「600 萬血池」與「攻擊力越高殺越快」，雙0血是唯一狀態。**

本體那批階梯觸發器省不掉。

### 5.6c 🔴 任務面板的排版限制（等級 A — 實機 2026-08-28）

**右上角任務面板寬度約 20 個半角字，超出就硬斷行，且會把數字切成兩半。**

| 文字 | 半角字寬 | 結果 |
|---|---|---|
| `亡魂之堡　剩餘血量：100000` | 21 | ✗ 斷成 `10` / `0000`，讀不出來 |
| `亡魂之堡 100％` | 14 | ✓ 有 6 格餘裕 |

原始血量最長 7 位數（`6000000`），標籤縮到 `血:` 也還是 19 個，貼著上限——
換字體或解析度就會再爆。**百分比最多 3 位數，永遠不會斷行**，故血條採百分比。

### 5.6d 血條不得進入 F4 任務清單（設計決策，使用者裁定）

本體有自己的任務文字。血條若設 `display_as_objective=1` 會塞進 F4 任務清單，
**擾亂原本的任務呈現，而且沒人會點進去看**。故：

| 欄位 | 值 | 理由 |
|---|---|---|
| `display_on_screen` | `1` | 右上角長駐顯示 |
| `display_as_objective` | `0` | 不進 F4 清單 |
| `description` | `""` | 同上 |
| `description_order` | `99` | 排在本體任務**下方**，不推移原有項目位置 |
| `mute_objectives` | `1` | 血條每 1% 更新，避免任務提示音／閃爍 |

**✅ 已實機確認（`01s` 2026-08-28）**：`display_on_screen=1` 搭配
`display_as_objective=0` **右上角仍然顯示**，且 F4 任務清單裡**不會出現**
（同一畫面的對照組 `display_as_objective=1` 那行則出現在 F4）。

**✅ 且本體根本沒有任務顯示**：5232 個觸發器中，`display_on_screen` 與
`display_as_objective` 皆為 **0 個**。作者全靠 `Send Chat` 與
`Display Instructions` 敘事。因此加入血條後：

- F4 任務清單維持**全空**（與原版一致）
- 右上角只會有血條那一行，**零干擾**

⚠️ `description_order` 的排序語意**未定**：`01s` 中 `order=99` 出現在 `order=98`
**上面**，但觸發器建立順序也是 02 在 02b 之前，兩者無法區分。
既然本體只有一個顯示項，此欄位不影響結果，暫不深究。

### 5.6d-2 🔴 血條必須只在最終戰期間顯示（設計決策）

血條的條件是**永不成立**（見 5.6b），所以它一旦啟用就會**掛在右上角直到遊戲結束**。
亡魂之堡是最終戰，開場第一秒就顯示「亡魂之堡 100％」是錯的。

✅ **已實機確認（`01t` / `01u` 2026-08-29）**：`enabled = 0` 的觸發器**不顯示目標**，
`Activate Trigger` 後才出現，`Deactivate Trigger` 後收掉。

用**觸發器開關**控制顯示：

| 時機 | 動作 |
|---|---|
| 檔案初始 | 血條觸發器 `enabled = 0` —— **停用的觸發器不顯示目標** |
| 魔王出現時（`[4926] 客棧` 之後） | `Activate Trigger` 打開血條 |
| 魔王被擊殺後 | `Deactivate Trigger` 收掉血條 |

同一組開關也應套用在那 100 個階梯觸發器上：最終戰之前它們不必評估，
`enabled = 0` 可省下 100 個觸發器的每 tick 條件檢查。

### 5.6d-3 血條必須隨距離出現／消失（設計決策，使用者裁定）

不只「最終戰期間」，**離開亡魂之堡附近血條也要消失**。
AoE2 沒有鏡頭位置條件，只能用**單位距離**判定，語意上也正確：
自己的角色在打魔王 -> 血條在；角色撤退或全滅 -> 血條收掉。

✅ **已實機確認（`01u` 2026-08-29，使用者回報通過）。**

血條本身仍是 `enabled=0` + 永不成立條件（避免刪除線），
改由兩個**循環**觸發器依距離開關它：

| 觸發器 | 條件 | 效果 |
|---|---|---|
| 顯示控制（循環） | `objects_in_area(近框, quantity≥1, source_player=1)` | `Activate Trigger` 血條 |
| 隱藏控制（循環） | `objects_in_area(遠框, quantity≥1, inverted=1)` | `Deactivate Trigger` 血條 |

**API 事實**：`objects_in_area` **沒有 `comparison` 參數**，反向判定靠
`inverted=1`（語意為「區域內少於 quantity 個」）。

🔴 **必須設緩衝區**：近框 ±12、遠框 ±16。
兩框之間兩個條件都不成立，狀態維持不變。若兩框同大小，
玩家站在邊界上血條會**每秒閃爍一次**。

🔴 **收尾順序**：魔王死亡時要**先 Deactivate 距離開關，再 Deactivate 血條**。
反過來的話，血條會在下一個 tick 被還在跑的顯示控制重新打開。

**階梯觸發器全程保持啟用**（不隨距離開關），這樣玩家走回來時
變數已經是最新百分比，不需要重新收斂。
順帶一個自我校正的性質：階梯依 pct 遞減建立，故 id 順序遞增 = pct 遞減，
一個 tick 內若有多個門檻同時成立，**最後執行的正好是最低的成立門檻**，
也就是正確值——所以階梯即使中途停用再啟用也不會顯示錯誤數字。
